# Android image generation audit — 2026-11-17

AWAI-2927 remains open. On the physical Awai Android API37 x86_64 device, current native Murakumo reports only text capability, with llama.cpp and Qwen3-0.6B-Q8_0. The owning model directories contain the text GGUF; this is not an exhaustive full-filesystem model inventory.

The isolated test-only Itonami QA app was authenticated using the existing unattended software test-identity path, with no real-owner approval substituted. A native generate request with modality image and the public prompt “A blue square on a white background” was rejected as local-inference-denied-or-unavailable. The image control was present but disabled with an unavailable-model explanation even with a nonempty prompt. Android loopback127.0.0.1:8770/v1/capabilities returned curl exit7 connection refused; the old shell media adapter expects this service, while the current Android provider rejects non-text requests.

[Observed capability and refusal](evidence/jun-1340/image-capability.json). Zero images were generated by this probe. Image synthesis, output display and generated-file save/readback were not verified. No remote image provider, archived Nix service or new model download was used to mask the missing Android path.

Resume AWAI-2927 with an Android-compatible image-engine adapter and the explicitly versioned encoder/denoiser/VAE model set, validating actual digests, supported memory/backend and declared operations. Then run a nonempty image request through Itonami→Murakumo, decode/display the actual output, save it and compare the re-read bytes/digest. Existing text-generation success does not qualify this path.
