## 2. ADR-0001 の分割

### 2.1 独立アプリへ移すもの（Murakumo 非依存の中核）

| 要素（ADR-0001 の記述） | 独立アプリでの位置づけ |
| --- | --- |
| 認証済み forge イベント（GitHub / Radicle）を不変の論理 RunRequest に正規化 | **Ingress**。そのまま移す。重複イベントの冪等化を含む |
| coordinator が broker 遷移を永続化し、安定した replica job を短命ランダム bearer の lease で配る。runner DID は 1 論理 run につき最大 1 replica。期限切れ requeue、古い token の拒否 | **Coordinator / Broker**。移す |
| runner DID の attestation と許可リスト | **Identity port**（2.4.2）。DID 検証は移し、DID の発行元を Murakumo 固定にしない |
| 不変 detached checkout → kotoba-git import → pipeline CID 検証 → argv のみのステップ | **Runner 契約**。実行サンドボックスだけ provider 化（2.4.4） |
| 宣言アーティファクトをホストが読んでハッシュ。runner 申告の ID は信用しない | 移す |
| receipt / verdict を kotoba-git オブジェクトにし、共有論理結果 ref に kotoba-rad sigref で署名。同一 DID の重複は閾値に数えない。割れた閾値はハードエラー | **Verdict quorum**。移す。アプリの中心 |
| CAS 保管（CID 再計算してから admission、完了時に CAS 存在を検査） | **CAS port**（2.4.3）。契約は移し、実装は差し替え |
| 耐久 outbox。外部効果は先に content-addressed outbox へ書き、成功後に delivered 印 | 移す |
| GitHub commit status は projection（context は `murakumo.cloud/ci`） | 移す。context 名は新アプリ名に変更（互換のため旧名を併記する期間は owner 判断） |
| `GET /ci/v1/runs/<id>` の quorum と delivery 状態 | **Read API**。ただし 4 章のとおりアプリ origin はサーバロジックを持てないため、coordinator の公開面は別ロール（4 章） |
| CD: 正確な ref の許可リスト、型付き release-bundle 1 つ、short-lived capability（RID・環境・verdict・current/previous CID・revision・時間窓・nonce）、宛先ノードが自前の issuer allowlist で検証、canary → バッチ昇格 → 逆順 rollback、署名付き rollout receipt | **CD engine**。移す。「ノード上の検証」は deploy-target port の契約にする（2.4.5） |
| 同一世代でのバックアップ（broker store と CAS）、秘密は環境変数名のみ参照 | 移す |

### 2.2 Murakumo 固有として provider 側へ残すもの

- Murakumo QUIC overlay 上の RPC セッション（`murakumo.overlay.quic-driver`。ランブックによれば JVM の kwik のみ、kbb では serve/dial 不可）
- Murakumo node daemon、`cd-node`、各ノード operations adapter
- `murakumo.artifact-store` / `artifact-replication` / `artifact-import`（Murakumo CAS 実装）
- kbb / JVM 前提の起動物（`kbb -M:ci-coordinator` など）と `examples/*.edn`
- Murakumo fleet 向けの capability 検証実装（宛先ノード側）

これらは新アプリでは「**Murakumo provider**」として、2.4 の port を実装する別パッケージにする。

### 2.4 port 定義（抽象）

実装言語は決めない。データ形は ADR-0001 の語彙（RunRequest、replica job、lease、verdict、receipt、release-bundle、capability）を保つ。

**2.4.1 Transport port.** 操作: `lease-claim`, `heartbeat`, `upload-chunk`, `complete`, `fetch-job`, `subscribe-status`。要件: 要求ごとに run ID・runner DID・lease token を束縛、再送で冪等、メッセージ長に上限（chunk 化）。実装候補は (a) HTTPS（fetch 可能、ブラウザ/Tauri WebView から使える）、(b) Murakumo QUIC（Tauri Rust 側のみ）、(c) WebSocket/WebTransport。選択は 5.7 と 6.4 の契約制約を受ける。

**2.4.2 Identity port.** `verify(signature, did, expected-rid/ref/verdict-cid)` と `runner-allowlist(rid)`、`delegate(account-did → runner-did, scope, expiry)` の検証。許可リストの出所は coordinator ポリシー（repo 単位）。Murakumo 固有の DID 発行は provider 側。

**2.4.3 CAS port.** `put(cid, bytes)` は CID 再計算に一致しなければ拒否、`has(cid)`, `get(cid)`, 世代単位のバックアップ。Murakumo store、ローカルファイル、WebDAV/AwaiVol 等を provider とする。verdict 参照オブジェクトが CAS にないものは完了させない（ADR 同様）。

**2.4.4 Sandbox port（runner 内部）.** `run(step, inputs-cid, limits, network=none) → outputs, exit`。ティアは 5.3。

**2.4.5 Deploy-target port.** `stage(bundle-cid)`, `canary(health)`, `promote(batch)`, `rollback(reverse-order)`, `receipt()`、および「宛先が capability を自前の issuer allowlist で検証する」責務。Controller が宛先の信頼ポリシーを渡してはならない（ADR 同様）。Murakumo provider はこの port の一実装。他の provider（SSH、Cloudflare、Tauri 端末の配布等）は別途。

## 4. システムの役割分離（ワークスペース契約に合わせる）

契約は「静的配信 origin、ブラウザがユーザー側で実行、外部サービスへは操作ごとの新規同意」。したがって次を別ロールとして混ぜない。

| ロール | 内容 |
| --- | --- |
| 静的配信 | UI の HTML/JS/Wasm のみ。リクエスト時ロジックなし |
| 端末アプリ | 閲覧、検証、承認、（選択により）runner |
| Coordinator サービス | broker / outbox / CAS / read API。**契約上は end-user app ではなく「remote protocol service / control plane」**。ユーザーが運営するリモートサービス |
| Runner fleet | 無人で動く実行系（Murakumo fleet 等）。end-user app ではない |
| Deploy target | provider（Murakumo 等） |

コーディネータは新設のコントロールプレーンであり、「アプリ origin はサーバ処理を持たない」の対象外と解釈するのは設計者の整理で、契約が明示的に認めているかは未確認（9 章 Q1）。

## 5. Awai OS 端末側の役割

### 5.1 クライアント役割

1. **Run viewer / evidence verifier（最も安全）**: coordinator の run 状態を読み、verdict の署名、RID/ref/verdict CID の再計算、CAS 参照存在、quorum（distinct DID のみ）をローカルで検証して表示。副作用なし。
2. **CD approver（phone）**: 昇格前に capability の内容（RID・環境・verdict CID・current/previous artifact CID・時間窓）を端末に表示し、ユーザーが承認すると**端末の鍵ではなく**承認の署名を返す。本番の capability 発行は coordinator の issuer が行う（5.6）。
3. **Runner（desktop / Android）**: 利用者のデバイスで replica を実行し、verdict に署名。

### 5.2 端末 runner DID

- アカウント鍵は複製しない。ユーザーの Awai identity からの**委任**で端末専用の runner DID を enroll する（scope: 対象 RID、サンドボックスティア、期限）。phone enrollment の既存方針（承認経路、秘密鍵のコピーや PIN の流用をしない）と整合する（`aosp-platform-decision-20261117.md`、`phone-link-design.md`）。
- 委任の失効・期限切れ後の署名は coordinator の許可リストで拒否。端末紛失時は許可リストから DID を除去（ADR-0001 の rotate 手順と同型）。
- 実際の enrollment 方式（Passkey / ウォレット / phone-link の流用可否）は未設計で Open Q。

### 5.3 サンドボックスティア

| ティア | 内容 | 対象端末 | 状態 |
| --- | --- | --- | --- |
| T0 verify-only | 実行せず検証のみ | desktop / Android | 設計可能 |
| T1 決定的 Wasm | Amu selfhost が生成した Wasm ステップ。ネットワーク・時刻・乱数なし、入力は CID 固定 | desktop / Android | 設計。Amu の出力が決定的であることは**未実測** |
| T2 rootless OCI | digest 固定イメージ、リソース制限、network なし | **desktop Linux のみ** | ADR-0001 と同じ。macOS / Windows / Android では不可とみなす |
| T3 microVM（Android） | — | — | **未認定**。アイデアとして記録するのみ。Android に rootless OCI はない |

既存の Awai OS 資産（Meiji VM の lifecycle、Android 実機）との関係は設計していない。

### 5.4 quorum に必要な決定性

verdict は「source、pipeline、終端結果、アーティファクトの正確な ID」を含み、runner 固有のタイミングやログは除外される（ADR-0001）。よって T1/T2 のステップは入力が同一なら出力バイトが一致する必要がある。非決定のステップ（時刻、並列順、ネットワーク）は quorum 対象外とし、**1 runner 完結の attested-only ジョブ**として扱う案を提示する（quorum 無しであることを表示で明示。Open Q）。ADR は 2 runner が別結果を出すと割れた閾値をハードエラーとするため、非決定を quorum に入れるとジョブが恒常的に失敗する。

### 5.5 Android 制約

調査していない実機挙動を含む。**未検証の一般論として**: Doze / App Standby による実行中断、バッテリーと発熱、従量課金回線、バックグラウンド実行には foreground service 等が必要になる、といった制約が runner の可用性を支配する。設計上は (1) 充電中・非従量 Wi-Fi・ユーザー設定の時間窓のみ受理、(2) lease を短くし中断時は requeue（ADR の lease 期限で自然に処理）、(3) 熱・電池閾値で自己停止、(4) Android runner は T0/T1 に限定、とする。具体的な OS API・閾値は実機で測定するまで確定しない。

### 5.6 秘密と本番権限

- 端末にはデプロイ資格・本番 issuer seed・forge トークン・webhook secret を置かない。capability の issuer は coordinator 側（または HSM 相当）で、端末は承認と検証のみ。
- 端末が扱うのは自分の runner DID 鍵と、ユーザーが承認した操作の同意だけ。

### 5.7 端末からの通信手段

| 経路 | 内容 | 契約との関係 |
| --- | --- | --- |
| WebView `fetch`（HTTPS） | 共有 `kotoba.app.client-runtime.v1` の broker 経由で宣言済みエンドポイントのみ | 契約どおり。操作ごと同意 |
| Tauri Rust 側 TCP/QUIC | Murakumo QUIC など非 fetch | **host-supported browser-operation 宣言が必要**。正本 broker が非 fetch をカバーするか**未確認**（6.4） |
| Android ネイティブ adapter | Yotei の例のとおり WebView↔ネイティブの限定 adapter。Yotei は INTERNET 権限なし | 通信が必要な本アプリは INTERNET 権限追加のレビューが要る（`yotei-tauri-v3-closeout`の方針と異なる点） |

## 6. ワークスペース契約との衝突（owner 決定事項）

### 6.1 契約の要点

静的 origin のみ。外部サービスへは「操作ごと」に新規・操作固有の同意（サービス、エンドポイント、操作、データ分類を表示）。拒否ならリクエストを送らない。承認は別の操作・エンドポイントへ流用しない。アプリ/Bot コードは承認を生成・永続・拡大できない。ブラウザの権限ダイアログは Kotoba の同意の代わりにならない。

### 6.2 衝突

**エンドユーザー端末で無人のバックグラウンド runner を動かすことは、操作ごとの同意と直接衝突する。** lease の取得、heartbeat、chunk アップロード、完了通知はすべて外部サービス（coordinator）への操作であり、人間が各操作の直前に承認する形では無人実行が成立しない。承認を一度にまとめる（セッション承認）ことは現行契約が許していない。

### 6.3 選択肢（owner 決定）

| 案 | 内容 | 契約変更 | 帰結 |
| --- | --- | --- | --- |
| A 受理は有人 | ジョブごとにユーザーが端末で「このジョブ（RID/ref/CID、データ分類、coordinator）を実行・結果送信する」を承認。1 ジョブ 1 承認で、lease・heartbeat・chunk・complete は同一の承認済み操作の一部と契約が認める範囲で束ねる | 解釈確認が必要（上記の「束ね」が契約内か） | 可用性は人の操作頻度に依存。quorum の速度が落ちる |
| B 有界セッション承認 | 「RID X のジョブを N 件・T 時間、この coordinator のみ」という有界な承認を 1 回で与える | **契約の変更が必要**（共有 runtime のセマンティクスと AGENTS.md） | 無人に近づくが、各操作の同意を弱める。owner が契約を改訂するかの判断 |
| C 無人 runner は fleet のみ | 端末は T0（viewer/approver）と有人 runner に限定し、無人 runner は Murakumo 等の fleet（end-user app ではない）に置く | なし | 契約に最も忠実。端末 runner の価値は限定的 |

推奨はしない（owner 決定）。ただし C は契約変更なしで直ちに進められ、案 A は解釈確認だけで進められる。

### 6.4 非 fetch 通信のブロッカー

QUIC など fetch を通らない通信は、契約により「host-supported browser-operation 宣言」を明示して直前に新規承認を求める必要がある。正本の broker（`kotoba-lang/kotoba/lib/kotoba.wasmWebcomponent/src/kotoba-client-runtime.js`、本 repo AGENTS.md は `wasm-webcomponent/src/...` と記すがパスが食い違っており、どちらも**今回読めなかった**）が非 fetch 操作の宣言をカバーするか確認できていない。**ブロッカーとして記録する。製品内に独自 broker・descriptor 検証・同意ロジックを置かない。** 未確認の間は fetch で成立する HTTPS transport だけを前提に設計し、QUIC 利用は fleet 側（アプリ origin 外）に限る。

## 7. フェーズと受入確認

各フェーズは「source / built candidate / device qualification / publication」を分けて記録し、一つの成功を他へ読み替えない。

| Phase | 内容 | 受入確認（測定可能） | 区分 |
| --- | --- | --- | --- |
| P0 | `tatara-core`（RunRequest 正規化、verdict CID 再計算、quorum 判定）を純粋ロジックで実装 | 負の対照つきテスト: 同一 DID 2 件で quorum 不成立、割れた verdict がハードエラー、CAS 欠落で完了拒否。ADR-0001 の失敗モード 8 項を各 1 ケース以上 | source |
| P1 | 読み取り専用 viewer（desktop Tauri / Web）。run 状態取得と CID・署名・quorum の端末内検証 | 固定フィクスチャ run を取得し、改ざん版（1 バイト違い）で検証が失敗すること。外部通信は宣言済み fetch のみで、拒否時に 0 リクエスト | built candidate → desktop 実機 |
| P2 | 有人の決定的 Wasm runner（desktop、T1）。案 A 前提 | 同一ジョブを 2 台（別 DID）で実行し verdict CID が一致して quorum 成立。出力が不一致なら失敗として表示。承認拒否で送信 0 | desktop device qualification |
| P3 | Android viewer と有人 runner（T0/T1） | 実機で P1/P2 の同じ受入。熱・電池・Doze 下での lease 失効→requeue を実測し記録 | Android device qualification |
| P4 | CD の phone 承認 | capability 内容（RID・環境・verdict CID・current/previous CID・時間窓）を表示し承認で署名が返ること、改ざん表示で承認不能、期限切れ capability を宛先が拒否 | device qualification（本番デプロイは別途） |
| P5 | provider-murakumo による既存 fleet への接続 | Murakumo provider が 2.4 の port を満たし、ADR-0001 の受入（quorum、outbox 再送、canary rollback）を新アプリ経由で再現 | built candidate → fleet qualification |
| 公開 | リリース・本番ルート切替 | 互換性とリリース証跡が揃い、owner が別途承認。この設計は承認ではない | publication |

契約が求めるとおり、既存の server ルートは移行インベントリとして扱い、本番カットオーバーは別承認とする。GitHub Actions 停止の暫定対応は、この設計と独立に、既存 Murakumo 実装の現行運用（ADR-0001 は Accepted）で行える範囲を別 issue で確認する（本設計では扱わない）。

## 8. 契約外の注意

- アプリ origin に API を置かない。coordinator は別ロール。
- ダウンロード（イメージ・Wasm・モデル）は外部操作。digest を検証し、digest が取れない場合は unverified として記録（契約どおり）。
- Bot のツール承認はブラウザ同意の代わりにならず、その逆も同様。
