# 近接端末の検出とペアリング（設計案）

状態: **提案、owner 決定済み**（2026-11-17）。追跡: [AWAI-3056](https://linear.app/kotobalabs/issue/AWAI-3056)。
この文書は設計案であり、実装・受入・承認を意味しない。owner が決める事項は末尾にまとめる。

## 目的

同じ LAN、Bluetooth の届く範囲、または Wi-Fi の直接接続ができる範囲にある Android／Awai OS 端末を見つける。
見つけた相手は既存の `awai.link.v1` の署名で本人確認し、アカウント連携と、その後の選択した同期につなぐ。
QR とリレーによる今の連携を置き換えるのではなく、近くにいる場合の別経路として追加する。

## 現状（main `ff51f9e`、2026-11-17 に確認）

- Android 版には近接検出の仕組みが無い。
- 連携は `android/client/identity-entry.js` の `awai.link.v1` だけで、次の流れになる。
  1. PC 側が QR と確認コードを表示する。
  2. スマートフォンが Passkey かウォレットで承認する。
  3. 応答は PC 側の鍵へ暗号化され、`relay.awai.network` を通って届く。
- Home と Itonami の間のサインイン共有、暗号化したプロフィールの転送、同期は未実装（`android/README.md`）。
- 旧 NixOS 版の mDNS、Bluetooth、音による連携は `archive/nixos/` に移され、Android には移植されていない。

実機で確認した機能（`pm list features`、2026-11-17）:

| 端末 | API | BLE | Wi-Fi Direct | Wi-Fi Aware | Google Play 開発者サービス |
| --- | --- | --- | --- | --- | --- |
| 6600H（Generic x86_64 診断イメージ） | 37 | なし（Bluetooth のみ報告） | なし | なし | なし |
| moto g05 | 37 | あり | あり | なし | 検出されず |

どの経路も全端末で使えるわけではない。そのため、使える経路を端末ごとに選ぶ構成にする。

## 方針

1. **検出と信頼を分ける。** どの経路で見つけても、それだけでは相手を信用しない。信頼は、両方の画面に出る短い確認コード（SAS）を利用者が照合し、その後 `awai.link.v1` の署名を検証して初めて成立する。
2. **見えるのは必要なときだけ。** 告知（advertise）は、ペアリング画面を開いている間だけ、最長 120 秒行う。常時表示の設定は設けない（owner 決定 2026-11-17）。
3. **固定 ID を流さない。** 告知には端末名、アカウント、DID を含めない。毎回変わるランダムなトークンだけを含める。
4. **操作ごとの同意。** 告知の開始、検索の開始、特定の相手への接続、データの送信は、それぞれ共有の同意 UI で明示的に承認を得る。拒否した場合は何も送らない。
5. **秘密鍵は移さない。** 端末鍵は各端末の Keystore／取り出せない WebCrypto 鍵のまま使う。連携は署名で行う。
6. **Google Play 開発者サービスを必須にしない。** AOSP 方針（AWAI-3007）に従う。Nearby は採用しない（owner 決定 2026-11-17）。

## 層の構成

| 層 | 役割 | 所有者 |
| --- | --- | --- |
| 1. 経路アダプタ | NSD、BLE、Wi-Fi Direct、Wi-Fi Aware で、相手のトークンとバイト列の通り道を提供する | ネイティブ Android（Home の Java、後に共通ライブラリ）。固定の操作 enum だけを公開する |
| 2. セッション | 一時鍵の交換、SAS の導出、フレームの暗号化 | `.cljc` の共通ロジックと WebCrypto。経路には依存しない |
| 3. 連携 | `awai.link.v1` の要求と応答。QR の代わりにセッション内で受け渡す | 既存の `otehon/shell/src/identity/link.js` |
| 4. 同期 | 選んだカテゴリの暗号化転送 | 既存の同期方針（`itonami-store-shared-install-sync-20261116.md`）と暗号化 envelope（AWAI-2924） |

ブラウザ側（WebView）から mDNS や生のソケットは扱えない。そのため層 1 はネイティブに置き、WebView には固定の操作だけを見せる。

```text
startAdvertise(transport, sessionToken)
startBrowse(transport)
stop()
connect(peerToken)
send(frame)
close()
```

どの操作も、ネイティブ側で使えないと判断した経路は拒否し、別の経路へ黙って切り替えない。

## 経路ごとの設計

### mDNS / NSD（同じ LAN）

- **Android:** `NsdManager` でサービス種別 `_awai-pair._tcp` を告知・検索する。
- **TXT レコード:** `v=1` と `t=<16 バイトのランダムトークンの base32>` だけを入れる。端末名には固定の「Awai」を使い、機種名や所有者名は入れない。
- **接続:** TCP で、ポートは都度確保する。
- **API 37 での要確認事項:** ローカルネットワークアクセスの実行時権限が必要になるか。マルチキャストロックが必要か。Ethernet でも NSD が動くか。6600H は有線のみ。
- **iOS（将来）:** `NSLocalNetworkUsageDescription` と `NSBonjourServices` の宣言が必要。
- **向いている場面:** 同じ家庭 LAN にある PC とスマートフォン。6600H で使える唯一の経路の見込み。

### Bluetooth / BLE

- **告知:** BLE で Awai 用の 128 ビット service UUID を告知する。service data には `v` と 8 バイトのランダムトークンだけを入れる。
- **接続:** GATT か L2CAP CoC。帯域を考えると L2CAP CoC を優先する案。
- **権限:**
  - 検索に `BLUETOOTH_SCAN`。位置情報に使わないので `neverForLocation` を付ける。
  - 告知に `BLUETOOTH_ADVERTISE`、接続に `BLUETOOTH_CONNECT`。
- **6600H:** Bluetooth は報告するが BLE は報告しない。そのため、BLE の告知と検索は使えない前提にする。
- **向いている場面:** 共通の LAN が無いスマートフォン同士。家電の Wi-Fi に入っていない場面。

### Wi-Fi Direct（P2P）と Wi-Fi Aware（NAN）

- **Wi-Fi Direct:** `WifiP2pManager` のサービス検出（DNS-SD over P2P）で `_awai-pair._tcp` を検索する。グループを作ったあと、そのグループ内の TCP で接続する。
- **Wi-Fi Aware:** `WifiAwareManager` で publish／subscribe し、データパスを作る。どちらの端末も Wi-Fi Aware に対応していないので、実装は対応端末が手に入るまで保留する。
- **権限:** `NEARBY_WIFI_DEVICES`（`neverForLocation`）。
- **注意:** Wi-Fi Direct のグループを作ると、既存の Wi-Fi 接続や画面のミラーリングに影響することがある。接続は利用者が選んだ相手に限り、終わったらグループを必ず解除する。
- **向いている場面:** 共通の LAN が無く、データ量が多いとき。プロフィールの初回転送など。

### Nearby（Google Nearby Connections）

**採用しない**（owner 決定 2026-11-17）。Google Play 開発者サービスが必要であり、AOSP 方針（AWAI-3007）と合わない。手元の 2 台でも検出されていない。Quick Share（旧 Nearby Share）もアプリ間のペアリングには使わない。

## ペアリングの流れ（PC とスマートフォン、初回）

1. PC の Awai Home で、利用者が「近くのスマートフォンから連携」を選ぶ。同意 UI で告知の開始を承認すると、使える経路で `sessionToken` を告知する。
2. スマートフォンの Android 版 Awai Home または awai-mobile（どちらもネイティブ。Web ページの `awai.network/link/` では mDNS も BLE も扱えない）で、利用者が「近くの PC を探す」を承認する。
3. スマートフォンが PC を見つける。一覧には「Awai PC」とトークン由来の短い記号が出る。利用者が選んで接続を承認する。
4. 両端末が一時鍵（P-256 ECDH。既存の WebCrypto と同じ曲線）を交換する。
5. 交換の記録（transcript）のハッシュから 6 桁の SAS を導出し、両方の画面に表示する。
6. 利用者が両方で一致を確認する。不一致や取り消しの場合は、セッションを捨てて何も送らない。
7. 一致後、PC は `awai.link.v1` の要求をセッション内で送る（QR で渡していた内容と同じ）。スマートフォンが Passkey かウォレットで署名し、今と同じく PC の鍵へ暗号化して返す。
8. PC は既存の検証器で署名・期限・端末の結び付きを確かめ、連携済みとして保存する。
9. 告知を止め、接続を閉じる。

この流れではリレーに接続しない。近接経路が使えない場合は、利用者が明示的に QR とリレーの経路を選ぶ。自動では切り替えない。

## 連携済み端末の再発見

- 初回の連携が成立したら、両端末で 32 バイトのペアリング秘密を合意して保存する。保存先は Keystore で保護した領域とする。
- 再発見のときは、トークンとして `HMAC(ペアリング秘密, 10 分単位の時刻)` の先頭 8 バイトを告知する。連携済みの相手だけが自分の端末だと分かり、第三者には毎回違う値に見える。
- 再接続しても、SAS と署名の確認は省略しない。代わりに、保存済みの相手の鍵で相互認証する。
- 連携の解除や端末の失効で、ペアリング秘密を消す。

## 同期への接続

- ペアリングが成立しても、同期は自動では始めない。同期するカテゴリ、方向、相手を利用者が選び、同意 UI で操作ごとに承認する（既存の同期方針どおり）。
- 送るデータは暗号化した envelope（AWAI-2924）か Drive の暗号化 CAR として、セッション内で送る。
- 競合、停止、失効のどの場合も、手元のデータを消さない。

## 脅威と対策

| 脅威 | 対策 |
| --- | --- |
| なりすまし・中間者（偽の告知） | SAS の目視照合と `awai.link.v1` の署名検証。告知の内容は信用しない |
| 追跡（固定 ID の告知） | 告知はランダムなトークンか時間で変わる HMAC だけ。告知は時間を限る |
| 盗聴 | 層 2 で全フレームを AES-GCM で暗号化する。経路側の暗号化に頼らない |
| 再送 | セッションごとの nonce、`awai.link.v1` の期限、一度使ったトークンの拒否 |
| 誤った相手への接続 | 一覧からの選択と SAS の一致の両方を必須にする |
| 妨害（大量の告知や接続） | 1 セッションの接続数と試行回数に上限を設け、時間で失効させる |
| 位置情報としての利用 | BLE と Wi-Fi の権限に `neverForLocation` を付け、スキャン結果を保存しない |

## 共有契約との関係

`kotoba.app.client-runtime.v1` の外部操作は、接続先の origin を事前に宣言する前提になっている。一方、LAN の相手のアドレスは事前に決まらない。そのため、次のような **ローカルピア操作** の型を共有の broker に追加する必要がある。

- 接続先は、検出したトークンに結び付いた相手に限る。
- アドレスはリンクローカル、プライベート（RFC 1918、ULA）、または P2P／BLE のグループ内に限る。
- 同意 UI には経路、相手の記号、送るデータの種類を表示する。

owner 決定（2026-11-17）により、この型は正本の Kotoba client runtime（`kotoba-lang/kotoba/lib/kotoba.wasmWebcomponent/src/kotoba-client-runtime.js`）に追加する。awai-os は固定した版を vendor して使い、製品側に同意の仕組みを複製しない。今の runtime は事前に宣言した `https://` の origin しか受け付けないため、この追加が P1 の前提になる。

## 段階と受入

| 段階 | 内容 | 受入テスト |
| --- | --- | --- |
| P0 調査 | 6600H と moto g05 で NSD、BLE、Wi-Fi Direct の告知・検索を最小のテストアプリで試し、必要な権限と制約を記録する | 各経路の成功・失敗と、出た権限ダイアログを日付付きで記録する。使えない経路は使えないと書く |
| P1 LAN ペアリング | NSD 経路で PC↔スマートフォンの SAS ペアリングと `awai.link.v1` の連携 | 拒否時は何も送らない。SAS 不一致で中止する。リレーに接続しない（通信を記録して確認）。再起動後も連携が残る |
| P2 再発見 | ペアリング秘密による再発見と相互認証 | 第三者の端末から、告知が毎回違って見える。解除後は見つからない |
| P3 BLE と Wi-Fi Direct | 共通 LAN が無い場面の経路 | moto g05 同士、または BLE 対応 PC で P1 と同じ受入 |
| P4 同期 | 選んだカテゴリの暗号化転送 | 操作ごとの同意。競合・停止・失効で手元データが残る |
| 任意 | Wi-Fi Aware | 対応端末が手に入ってから |

## owner の決定（2026-11-17）

1. **Nearby:** 採用しない。経路は NSD、BLE、Wi-Fi Direct、Wi-Fi Aware に限る。
2. **ローカルピア操作の型:** 正本の Kotoba client runtime に追加する。awai-os は固定した版を vendor して使う。
3. **スマートフォン側の実装場所:** Android 版 Awai Home と awai-mobile の両方。
4. **告知の範囲:** ペアリング画面を開いている間だけ（最長 120 秒）。常時表示の設定は設けない。
5. **確認コード（SAS）:** 6 桁の数字。

## 未確認事項

- 6600H の Bluetooth が BLE の告知・検索に使えない理由。ドライバかイメージの設定か。
- iOS 版を作る場合の Bonjour と CoreBluetooth の制約。バックグラウンドでの検出は制限される。
