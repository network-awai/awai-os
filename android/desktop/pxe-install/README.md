# PXE persistent install for the 7735HS (AWAI-3585/AWAI-3586)

A decision-ready disk plan plus a PXE installer profile that delivers a
persistent Awai OS PC installation over the direct LAN without touching any
existing boot entries. All destructive steps stay the owner's hand.

The 7735HS NVMe (512-byte sectors, 500118192 sectors) currently holds:
p1 otehon-esp 2048-2099199, p2 otehon-root ext4 2099200-52430847 (24 GiB,
hosts `/awai-android-2992`), p3 otehon-state LUKS 52430848-500118158
(~213 GiB). Free range: only 34-2047 (2014 sectors, nothing aligned), and
`awai-pc-install.py plan` refuses: need 60082176 sectors (28.65 GiB, 16 GiB
userdata) in one aligned range. See [evidence/disk-plan-20261123.json](evidence/disk-plan-20261123.json),
generated by `generate-disk-plan.py` from the recorded GPT, exercising the
real `make_plan()` with `table()` mocked the way `test_awai_pc_install.py`
does (sgdisk is not on the operator Mac).

## Disk options (sector-exact)

| Option | What happens | Destroys | Plan |
| --- | --- | --- | --- |
| (a) Erase `nvme0n1`, install A/B fresh | free [2048, 500118158] = 500116111 sectors ≥ 60082176 | p1 ESP, p2 (root + `/awai-android-2992` persistence images), p3 LUKS — total loss; needs encrypted backup of p2 contents and p3 first | ok, 11 partitions (plan in evidence JSON) |
| (b1) Shrink only p3's tail | p3 end → 440035327, new free [440035328, 500118158] = 60082831 sectors ≥ need | LUKS tail 28.65 GiB truncated (volume + filesystem shrink + backup first); LUKS header + p1 + p2 preserved | ok (11 partitions) |
| (b2) Shrink p2 alone | max frees 50331648 < 60082176 | even *deleting* p2 cannot fit this layout | impossible — installer needs a single range bigger than all of p2 |
| (b3) Free a gap before p3 | requires moving p3's start (LUKS header lives at p3 start) | destroys the LUKS header ⇒ identical to losing all of p3 | not viable |
| (c) Second disk | blank-disk free [2048, 500118158...] (any 512e disk ≥ 60084257 sectors; recommend ≥ 64 GiB) | only the new disk; current NVMe untouched — recommended if labelling matters | ok, 11 partitions |

The KVM 2026-11-19 source sizes total *exactly* 60082176 aligned sectors,
matching the pinned cd22c762 candidate total, so the cd22c per-partition
split is almost certainly identical — but only its total is pinned; the
exact cd22c placement needs its stock disk image (missing input, see below).

## PXE install profile

New, additive profile beside the five existing entries. Nothing existing
is replaced; the firmware route (`activate-route.mjs`/`switch-route.mjs`)
decides which artifact directory is live, and the operator switches it back
afterward.

- `../persistence/patch-ipxe.mjs <in> install <out> [erase|shared] [sectors]`
  — same port/blacklist ops as the other modes; appends only a short
  `awai.install.profile/mode/sectors` marker. Image sha/bytes/url pins live
  inside the initrd overlay (`/awai/install.pins`, template
  `../persistence/install.pins.template`), digest-covered by the serve
  manifest's whole-initrd pin — never long cmdline text the embedded
  region cannot grow to hold (the script refuses loudly if it can't fit).
- `../persistence/serve-install.mjs <dir> <manifest.json>` — same static,
  manifest-pinned server as `serve-artifacts.mjs`, plus `install.img`,
  on the same 10.77.0.1:18091.
- `../persistence/init-install.sh` — BusyBox init with the same guard
  style as `init-persistent.sh`: exact NIC MAC 0c:47:a9:60:9d:34, boot-mode
  marker on cmdline, one NVMe namespace of `awai.install.sectors`, root/LUKS
  UUID checks *before* any write (erase mode), every other local disk
  refused, and — before anything is written — the fetched bytes' SHA-256
  must equal the pin. The write itself additionally needs the operator to
  type the full SHA-256 on the console (destructive writes are the owner's
  hand, not an unattended default). After the write it re-hashes the
  written range and only then prints `AWAI_INSTALL_COMPLETE`. Default mode
  is `erase` (full-disk image, GPT carried inside the image — no
  runtime partition editor needed). `shared` mode refuses explicitly until
  a staged `/awai/sgdisk` GPT-splice writer is implemented; it never
  silently falls back to erase.

## Missing inputs (board-level blockers)

Full audit: [evidence/inputs-audit-20261123.json](evidence/inputs-audit-20261123.json).

None of these exist on the operator Mac, and several cannot be produced
here: signed target-files zip (signing record SHA-256), stock `disk-vda.img`
(build-record SHA-256), `otatools` (`build_super_image`/`lpmake`/`simg2img`),
AOSP releasetools, OTA key basename + certificate SHA-256, the install
image itself, the pinned iPXE binary, kernel/initrd for the initrd overlay,
and a second disk. Only `aapt2` (SDK 36.x, not on PATH) and internet
exist. The existing PC OTA pilot assumes Cloudflare R2 (`awai-os-ota`),
which conflicts with the owner no-R2 policy — the install route itself
does not need R2 (served from the operator Mac), but any OTA publish needs
the non-R2 decision first.
