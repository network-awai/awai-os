# Awai Home and Itonami Store — Otehon Android host

Implementation of Figma native UX v2 for Awai OS on Android AOSP, with a shared browser UI/domain. Device bring-up may reuse upstream community device trees; the product is presented only as Awai OS. This is a development build, separate from the Native selfhost profile.

To run Awai OS on an emulator, a PC or a phone, start with [BOOT.md](BOOT.md).

- `network.awai.home`: reversible Android HOME-role launcher, real installed-app drawer/launch, clock, local agenda projection and system-settings entry.
- `network.awai.store`: signed bundled catalog, library/update state, independent native confirmation, bounded APK digest/package/version/signer checks and Android PackageInstaller user action. Automatic updates (AWAI-3653, contract amendment kotoba-lang/kotoba#1365) are being added in steps; so far only the eligibility decision exists (`shared/src/network/awai/platform/UpdatePolicy.java`, tests `bash android/tests/update-policy.sh`). Nothing calls it yet, and every install still asks the person.
- `network.itonami.yotei`: actual bundled calendar application; shared browser UI and local event model, persistent local storage, signature-permission protected read-only agenda projection. No sync, remote inference or notification scheduling is claimed.
- `network.itonami.torihiki`: Torihiki devnet client listed in the bundled Store catalog (not preinstalled). UI (AWAI-3415, Figma `315:2`): 取引 / チャート / 口座 tabs and an order ticket. Reads: `/head`, `/market?id=1`, `/book?market=1&depth=15`, `/trades?market=1`, `/candles?market=1&span=1|10|50` and `/account?id=<own derived id>`. Devnet orders (AWAI-491): an Ed25519 session key generated in the WebView with a non-extractable private half, kept in IndexedDB; the account id is `torihiki.address/derive` of the raw base64 public key; transactions (`deposit` faucet, `order`, `cancel-all` on market 1) are signed over `torihiki.auth/signing-payload` and sent as `POST /tx`. The field count follows the node's `/head` code-version (`NODE_PROTOCOLS`): the deployed devnet (code-version 12) signs f0..f15 and has no cancel-all; unknown versions are refused (AWAI-3442, `docs/evidence/torihiki-devnet-trade-awai3442-20261118/`). The 50-field engine vectors stay as the reference. Nothing is signed unless this session's `/head` chain id names a devnet. Every request goes through the canonical broker with its own each-operation consent; the host allows only those routes (POST only for `/tx`) and the page CSP only that origin. Golden vectors from the engine: `android/tests/torihiki-vectors.json`. The live node is a single sequencer with unbacked devnet collateral; no real assets.

- Home has INTERNET permission for the fixed Awai account-link relay route. Store has INTERNET only in its explicit online build; Yotei remains offline. No ROM, SystemUI, Keyguard or existing launcher is replaced/uninstalled.
- Browser UI/state/domain use local JavaScript and compiled shared `.cljc`; Java contains platform operations and an independent installer trust boundary. Browser consent never grants host install authority.
- Canonical Kotoba runtime is copied unchanged from the existing revision/digest-pinned source bundle. Home declares one bounded relay GET with fresh operation consent; offline Store/Yotei declare no external operations. Strict CSP and the native request filter retain the fixed local asset origin and reject arbitrary file/content URLs or remote navigation.
- Catalog signatures use the local Android debug identity for this development build. This is not a production publisher/key-rotation release.

## Build

Installed macOS SDK prerequisites: platform37.0, build-tools36.1.0, OpenJDK27.0.1, Clojure CLI1.12.5.1654. The shared compiler dependencies are pinned in `client/deps.edn` (Clojure1.12.1/ClojureScript1.12.145). Local Babashka1.12.218 tests are additional evidence, not a fallback.

```sh
bb -cp android/contracts/src:android/contracts/test -m itonami.store.domain-test
cd android/client
clojure -M:build
cd ../..
node --test android/tests/domain.test.mjs
python3 android/build.py --version 1 --skip-cljs
python3 android/build-tests.py --version 1
```

Account linking also requires the owning shell’s lockfile-pinned npm dependencies: run `npm ci` inside `otehon/shell` before building. `android/build-identity.mjs` bundles the existing awai.link.v1 verifier, device-key custody and QR renderer; the canonical runtime stays an external, digest-checked module. `--home-only` builds Home without rebuilding Store/Yotei.

### Signing key and release builds (AWAI-3761)

By default `build.py` signs the APKs and the catalog with the local Android debug identity and builds debuggable APKs, as before (`signing: local-android-debug-only`). Another key is given with three options together:

```sh
export STORE_KS_PASS=...   # set it without echoing; the value is never put on a command line or in a report
python3 android/build.py --version 1 --skip-cljs --release \
  --keystore /path/to/keystore.p12 --key-alias <alias> --keystore-pass-env STORE_KS_PASS
```

`--release` builds non-debuggable APKs (`signing: release-key`, `debuggable: false`) and refuses the Android debug identity, a missing password variable, an APK whose single signer is not the given key, and a debuggable result. The keystore may be JKS or PKCS12; the keystore and the key use the same password. `python3 android/tests/release-signing.py` checks all of this with a throwaway key (about two minutes; nothing is installed or published).

Key list (AWAI-3775, design `docs/otehon/itonami-store-key-list-design-20261122.md`): the Store pins a root public key and a root-signed list of catalog and pointer keys. `python3 android/key-list.py` exports a key's public key (`export`), writes the list text and the facts for a sign request (`prepare`: SHA-256, sequence, validity, key IDs per role), signs exactly that text with the root (`sign --expected-sha256 … --expected-root …`), and checks a result with the Store's rules (`verify`). Key IDs are the SHA-256 of the SubjectPublicKeyInfo. `build.py --key-list DIR --catalog-keystore K --catalog-key-alias A --catalog-pass-env NAME` bundles the root and the list into the Store, signs the bundled catalog with that catalog key (refused unless it is listed, and never the APK key) and reports `trust`. By default the build uses the published development list (`store/keys/store-root.der`, `store/latest/keys-envelope.json`) and the development catalog key in `~/.android/awai-store-dev` (see `store/keys/README.md`); without that key it stops. `publish-latest-pointer.py` signs with a listed pointer key (default: the development pointer key) and refuses a key the list does not list for the pointer role; `android/sign-catalog-envelope.py` signs a distribution catalog of any number of apps with a listed catalog key. `python3 android/tests/key-list-signing.py` checks all of this with throwaway keys (about ten minutes with the full build; nothing is installed or published).

Release boundary: no production key or production rotation/revocation operation is qualified here. The current key-list profile separates APK, catalog and pointer signing roles: `build.py` refuses configuring the same resolved keystore path and alias for the APK and catalog roles and requires the catalog key to be listed for that role. Trust in development catalogs and pointers follows the configured root-signed key list, separately from the Store APK identity. A Store APK signed by a different signer cannot update a development Store in place. The ordinary supplied `--*-apk` inputs are checked against the configured APK signer (not the catalog key), so a development-signed input is refused when a different release APK signer is configured. Dedicated pinned-signer inputs, such as Registry Assoc, have their own admission path. `build-tests.py` still signs the instrumentation APK with the debug identity.

Build outputs, signed APKs, public fingerprint/digests and tool logs stay in `.agent-output/android`. The existing debug key stays in Android's credential directory and is never copied to source or reports. `build.py` never connects to or installs on a device.

The build generates tokens/CSS/resources from one shared palette, compiles shared domain functions once for both browser clients, and packages original Figma assets. Raw SVG dimensions are retained:24px controls,28px Store header source and64px featured calendar source. API-supplied installed app icons remain dynamic. Design-time Aozora/Murakumo/Itonami placeholders are not advertised as installable without actual release artifacts.

The launcher remains an ordinary app. Before default-HOME selection, record the previous component/role. Use Android's role selection UI to opt in; keep the existing launcher installed as rollback. Never assume adb selects the right phone: all device commands require an explicit serial.

## Explicit online development build

Store is offline by default. Home’s separately declared account-link relay is available in either build. `python3 android/build.py --version 5 --skip-cljs --online-pins android/online-pins.dev.json` includes a fixed immutable catalog source plus one APK pin per app id (`apks`, AWAI-3313) and additionally grants INTERNET to Store. Each pinned app gets its own consented download operation (`download-apk-<app id>`); each pin is capped at 64 MiB in the browser and again by that app's `Catalog` budget on the host. The host admits an online catalog only when every pinned app is listed with exactly the pinned android digest. The canonical runtime broker handles each real browser download, with exact paths, no credentials/referrer, no redirects, byte bounds and expected digest. Browser signature/expiry/revision verification is followed by independent Android catalog/identity verification and OS install confirmation. Denial sends no request; an app/bot must not synthesize the trusted user's approval.

The public development payload is under `store/distribution/dev-20261116` at commit `2cbd32f31b3053fd148e04dda25cbfd8e2f0b726`. Pins are immutable and must not be changed to `main` or an arbitrary URL. The signed catalog is revision100 and expires30 days after packaging. `store/distribution/dev-20261118` adds revision102 (Yotei, Itonami, Torihiki Bot) and the Torihiki Bot APK; Revision103 (`store/distribution/dev-20261118-r103`, AWAI-3320) adds the Torihiki devnet viewer. `android/online-pins.dev.json` now pins commit `30d2f1543aacdb585d460c0cf2dbf5ecbed4fb08`: revision104 (`store/distribution/dev-20261118-r104`, AWAI-3397), which adds Deai, and APK pins for all five apps. Revision102 was verified on an emulator (`docs/evidence/torihiki-bot-online-awai3313-20261118/`). The revision103 pins were then installed on an emulator (Torihiki, `docs/evidence/torihiki-online-awai3320-20261118/`). Revision 105 adds the release-signed arm64 Itonami Registry Assoc APK. It requires the updated Store host, which pins the Assoc release certificate independently of the development catalog key. A pin must name a commit that already contains the files, so new artifacts land first and the pins follow in a separate change. No production key rotation/revocation or automatic mutable latest channel is claimed. Browser-state and host-state failures remain visible; cached signed APKs can be installed offline with fresh native/OS confirmation.

Use `--bundle-registry-assoc` to include the exact release-signed Assoc APK
from revision 105 in a development Store build. This works alongside an
older accepted online catalog. A newer online Assoc version uses the online
path. Store verifies the local APK against its catalog and release
certificate and requests Android installation confirmation. A bundled
install makes no GitHub request.

`node --test android/tests/domain.test.mjs android/tests/online.test.mjs` checks compiled domain behavior, exact URL scope, signature alteration, metadata expiry and revision floor. Build/runtime/online/NixOS evidence remain separate. See `docs/otehon/itonami-store-shared-install-sync-20261116.md` for the common auth/permission/sync recommendation and current native-Nix/sync boundaries.

## Android setup and account linking

Home follows the existing Figma Android setup composition. Android Settings owns the actual language, networking and screen lock; Awai never receives the PIN. The account step uses the existing `awai.link.v1` phone/wallet/Passkey protocol through `https://relay.awai.network/v1/<32-hex-topic>/json`. Each attempt requires the canonical broker’s direct user consent before its GET; native filtering and CSP independently restrict the route. No approval or private key is imported from a fixture.

A saved signed link is reverified for expiry, device binding and the non-exportable device key’s possession before it can restore an authenticated account. The native setup preference is only a flow marker, not an identity credential. Invalid or missing proof returns to account linking while retaining saved evidence. Explicit account deferral remains available. Home’s WebView and Itonami’s WebView have separate stores: shared sign-in, encrypted profile transfer and sync are not implemented by this change.

See [the qualification record](setup-qualification-20261117.md) for current VM, real-account and physical-device gates. An ordinary Home APK is not privileged SetupWizard integration or a qualified persistent PC ROM.

## 営トレース development APK

Build the standalone [営トレース](https://github.com/network-awai/app-itonami-agent-trace)
app and read the SHA-256 printed by its build. Add it to the signed bundled catalog
with `--agent-trace-apk <apk> --agent-trace-sha256 <digest>`.
Store admits only the `network.itonami.agenttrace` package with the development signer,
the pinned digest, zero requested permissions, and an APK of at most 2 MiB.
OpenTelemetry and Langfuse trace files are reviewed and exported on the device.

For an APK built with a pinned trace feed origin, include `--agent-trace-online`.
The Store then requires exactly INTERNET in addition to the APK identity and
digest checks. This flag only configures the signed bundled catalog.
