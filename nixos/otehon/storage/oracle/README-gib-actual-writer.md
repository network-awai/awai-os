# Actual conditional 1 GiB Forest writer: hosted oracle

On 2026-11-14 macOS arm64, Babashka 1.12.218 and the pinned Forest tool (SHA-256 `e5fb23076a46c055142b3dbf3efa1ad5a68532d14419ad9994785986719b205f`) ran `gib_actual_writer.clj` against a new isolated store. The source contained exactly 1,073,741,824 logical bytes, with a distinct four-byte marker at the beginning of each 1 MiB chunk and zeros elsewhere. The actual `put-file-large!` used the observed root generation and published 64 Packs and manifest `bafyreidk3dxbsrqaocvdhfr624j4n75v6ddgmyfgkyu24z3lirlg5aj4g4`. The writer's measured interval was 100,713 ms, including staging, compression, validation, source recheck and publication.

A separate Babashka process recovered the group with an empty process-local handle cache, read the full 1 GiB in 1 MiB ranges and compared SHA-256 to an independent streamed hash of the original source. Both were `1f7e0c0d3fefe5579e556a04f7796b7de01278916e49a6d31df864e16adf1708`; the measured reader interval was 79,038 ms and includes the source hash. A copied store with one `.forest` archive withheld failed with `:missing-forest`; original and copy are retained. The first full read reached comparison but the existing `forest-source-digest` helper rejected the GiB input because it is bounded for archive files; a streaming input SHA implementation was used for the successful retry.

`du -sk` observed 532,496 KiB allocated for the source, 1,115,648 KiB for retained staging, and 440 KiB for the final store. These are one-host observations with highly compressible synthetic zeros, uncontrolled OS cache and other host activity. They are not a general throughput, compression, capacity or cold-I/O benchmark; they do expose staging overhead. This uses the existing 1 GiB/64-Pack upper bound, a hosted local single-writer profile and process restart, not Native, OS reboot/cache loss, physical power failure, distributed placement, a generic unbounded stream or production acceptance.

With a fresh private `GIB_ACTUAL_OUTPUT` and the pinned `FOREST_TOOL`, run the script once with `write`, then in a fresh process with `read`, using the Otehon storage and vendored apex/car source paths. Staging and all test evidence are retained under `.agent-output/gib-actual-writer-01`; the missing-Pack copy is separate. Do not infer successful host power loss from a process restart.
