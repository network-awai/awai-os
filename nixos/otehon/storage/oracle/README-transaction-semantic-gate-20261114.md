# Hosted transaction semantic gate, 2026-11-14

`open-transaction` retains its three-argument `:publish!` compatibility form. Its new four-argument form takes a trusted host verifier `(fn [get-block next-cid])`: after persisting the batch and checking its acknowledgement, but before attempting the ref CAS, the transaction requires literal `true` from that verifier. A false result, exception, or non-function refuses publication and closes the transaction. Persisted immutable blocks can remain orphaned. This is an opt-in application boundary, not an automatic semantic verifier for all callers and not an atomic multiple-Pack transaction. The verifier and subsequent CAS are not a single lock against concurrent GC; no concurrent GC safety is asserted.

The hosted receipt oracle uses this form to fetch and verify canonical request and signed manifest, their CIDs, signature and expected basis before ref CAS. It separately checks persisted causal receipt and bundle after publication. In fresh `.agent-output/pg24`, deliberately hiding the request from the gate refused the ref; allow and deny receipts recovered after a clean PostgreSQL restart/new JVM and signature checks passed. The check's semantic hiding models a missing fetch; it is not a physical archive corruption test. The prior negative tests (injected writer failure, no evaluation on denial) also passed. Focused transaction tests: 5 tests / 38 assertions, both hosted Clojure JVM and Babashka 1.12.218. Both are Otehon paths, not Native.

The request/manifest checks do not by themselves provide semantic graph tracing for all root namespaces, GC protection, independent witness, signed logical data commit, or atomic publication across multiple Pack files. Existing legacy callers and the three-argument API still have only their configured backend verifier. Test keys, time and nonce remain fixtures.
