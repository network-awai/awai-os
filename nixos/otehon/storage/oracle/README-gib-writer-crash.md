# 1 GiB conditional writer: process-kill and retry

On 2026-11-14 macOS arm64, Babashka 1.12.218 and the pinned Forest tool ran `gib_writer_crash.clj` against a task-owned copy of the already published Otehon 1 GiB/64-Pack store from `README-gib-actual-writer.md`. The candidate was a different 1 GiB synthetic sparse file, with unique per-MiB markers; the original store and both staged inputs were preserved. The writer used the observed generation 2 as its local conditional publication precondition.

The observer marked `{:event :half-written, :role :forest, :ordinal 32}` while the 32nd new Forest archive was being published. The identified Babashka writer process received SIGKILL and exited 137. A fresh process reopened the store: root generation remained 2, the old manifest remained `bafyreidk3dxbsrqaocvdhfr624j4n75v6ddgmyfgkyu24z3lirlg5aj4g4`, all 64 old Packs were present, and a full 1 GiB read gave SHA-256 `1f7e0c0d3fefe5579e556a04f7796b7de01278916e49a6d31df864e16adf1708`. A copy of the post-kill store, including retained partial/unreferenced objects, was preserved before retry.

A fresh conditional retry using a new staging directory published generation 3, 64 Packs, and manifest `bafyreif6pmypdch4ridmv4zubv2sbpylbxjidbfl644spzlzgauzhpd7sm`. A further fresh process read all 1 GiB and compared its SHA-256 `0fd9be4bed103a9379d9d3a1d434fbd6cbd229ae1f90e962baeeccadffcf9871` against a separate streamed digest of the new source. The baseline, interrupted output, retained partial files, retry and test inputs remain under `.agent-output/gib-writer-crash-01`.

Reproduction: create a fresh task-owned directory and copy the previously validated 1 GiB store to its `store` subdirectory. Set `GIB_CRASH_OUTPUT` to that directory and `FOREST_TOOL` to the pinned real tool; run `prepare` and then `write` in a child Babashka process with Otehon storage and vendored apex/car classpaths. Wait for `boundary.ready`, verify the child identity and send SIGKILL to that child. Run `verify-old` in a fresh process, preserve the interrupted store, run `retry`, then `verify-new` in another process. The observer is a test hook; no host Python gate or Native runtime fallback is involved.

This is one controlled process-kill point during a 64-Pack publication, not exhaustive crash coverage or a device/OS power-loss test. The source is highly compressible synthetic data, cache is uncontrolled, and the local lock is single-host CAS, not distributed fencing. It does not establish Native writer behavior, user-volume migration, production certification, or host OS cache loss.
